# What ePaperclip adds to Paperclip (and what it does not)

Baseline: native `paperclipai` **2026.1023.0** (the pin in `engine/package.json`). Upstream capabilities are taken from that package's own API (989 operations, `docs/evidence/parity/native-openapi.json`), its source in `node_modules/@paperclipai/*`, and live calls to a reference instance. Evidence labels as in [PAPERCLIP-PARITY-MATRIX.md](PAPERCLIP-PARITY-MATRIX.md): source-only, simulated, real Paperclip runtime, physical Proxmox+Orion hardware, real external provider or network. Proxmox is the repo's fake in every run made for this document, so nothing below claims a real hypervisor result that this work did not observe; other evidence is cited from the ledger and marked as not re-verified.

Classification: **new** = upstream has nothing comparable; **extension** = built on a mechanism upstream already supports, adds a layer; **integration** = better wiring of a supported upstream feature; **UI only** = different presentation of the same thing.

## Would a Paperclip user lose anything?

**Yes, in specific places, mostly because the host proxy only opens the engine routes the console calls and never serves the native UI.** A user who only creates organizations, hires agents, assigns work, watches runs and approvals, and sets budgets keeps all of that: the journeys give the same results on both, 37 of 37 native checks and 34 of 37 on ePaperclip, the three misses being closed routes. Capabilities with no ePaperclip equivalent today (regression rows in the parity matrix):

| Row | Lost | Why | Proposed owner |
| --- | --- | --- | --- |
| P04 | Company import / export | all `/companies/import*`, `/export*` closed, no screen | console + engine-client |
| P06 | Edit, achieve or delete a goal | `/goals/{id}` closed | engine-client + console (small) |
| A06 | Agent API keys | `/agents/{id}/keys` closed | needs a security decision (keys for external agents) |
| A07 | Agent config revisions and rollback | closed | console |
| R03 | SSH and local execution environments | environments list/create closed; managed-sandbox-only is on by design | product decision: either document it as an intentional limit or expose SSH environments as managed |
| J03 | Project workspaces and repositories | closed | console |

Further, smaller losses are marked **incomplete** (org chart image export, clear agent error and session reset, provider trace, finance and quota cost views, external secret providers, issue tree control, plugin config and health pages).

**Fixed in this PR.** Project edit and private-project access members were closed at the proxy: an owner could not grant a person access to a private project. `/api/projects/{id}` and `/api/projects/{id}/access-members[/{memberId}]` are now allowed (engine-allow.ts and engine-client, kept equal by the existing test); the engine's authorization still decides: a viewer is refused (`access` A09) and the grant works for the owner (A10, A11). The console still needs a screen for private-project membership.

**Private tasks and projects.** The managed-account proxy preserves them. It forwards as the signed-in person's own engine account (not a shared service account), so the engine hides a private project and its tasks from a viewer both in lists and by id (`access` A04, A12, A13 on both targets). The one caveat: every Proxmox administrator is an engine instance admin and therefore sees all organizations (A08).

**Nothing found replaced by a simulated response.** No ePaperclip route returns canned engine data in these runs; every engine call went to the real pinned engine.

## Blocked or not testable here

- Provider-backed runs (claude_local, codex_local, ...): owned by another agent.
- Real Proxmox, real Cloudflare, real Connect: not available to this work.
- The http adapter against a local stub: the pin refuses loopback and private targets (SSRF guard) on both targets (`journey` J28b), so a stub run is not possible; the process adapter was used instead.
- Timer-based heartbeats, timer scheduler admin view, WebSocket live events, the onboarding wizard's model step.
